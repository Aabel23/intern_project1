# BLE GATT provisioning transport (Android Kotlin ↔ Pi BlueZ) and Wi-Fi configuration with rollback on Raspberry Pi OS

Scope note: written 2026-10-12 for contract `contracts/messages/bt-claim.md` (B-03, still BLOCKED) and tasks M-01 / A-02. Repo facts checked locally: the existing machine code (`version1.1/machine/pairing/machine_bluetooth_serve.py`) is **classic Bluetooth SPP/RFCOMM** via `org.bluez.ProfileManager1.RegisterProfile` + `AgentManager1`, using `dbus-python` + `gi.repository.GLib` main loop, with `RequireAuthentication=True`. The contract now requires a **BLE GATT** service (RX write-with-response, TX indicate), no bonding. So the BLE server is a rewrite of the transport layer, not an adaptation; only the D-Bus/GLib skeleton (adapter discovery via ObjectManager, `Powered` set, main loop) is reusable.

Several primary-source domains (punchthrough.com, networkmanager.dev, raspberrypi.com, packages.debian.org) were unreachable from the research sandbox (DNS failure). Equivalent primary material was fetched from GitHub mirrors where possible (BlueZ docs, NetworkManager introspection XML and headers). Claims that rest on prior knowledge rather than a fetched source are put under **Inferences** and marked "(unverified)".

## Q1. Pi-side BLE peripheral: library choice, BlueZ version, MTU/indications/512, systemd/permissions

### Takeaway
Keep **dbus-python + GLib** (already in the repo and what BlueZ's own `test/example-gatt-server` uses) and implement `GattManager1.RegisterApplication` + `LEAdvertisingManager1.RegisterAdvertisement` directly; third-party wrappers (bless, bluezero, bluez-peripheral) add little for one service/two characteristics and hide the per-write `mtu`/`device` options and the indication `Confirm` callback that the contract relies on. Target BlueZ 5.66 (Bookworm) and 5.82 (Trixie).

### Cited Findings
- BlueZ versions: Debian bookworm ships BlueZ **5.66-1+deb12u2**; trixie ships **5.82-1.1**; sid/forky have moved to 5.84–5.85 — [Debian Package Tracker](https://tracker.debian.org/bluez); [aptpeek trixie](https://aptpeek.dev/debian/trixie/main/i386/bluez). Raspberry Pi OS rebased on Debian 13 "Trixie" in October 2025 — [Phoronix](https://www.phoronix.com/news/Raspberry-Pi-OS-Debian-13); [RaspberryTips](https://raspberrytips.com/raspberry-pi-os-trixie-released/). Exact BlueZ build in Raspberry Pi OS's own archive (RPi may carry a patched package) was not verified.
- `RegisterApplication` requirements: "the standard DBus.ObjectManager interface must be available on the root service path"; children implement GattService1/GattCharacteristic1/GattDescriptor1 + Properties; if bluetoothd sees `InterfacesRemoved` for a service "it will immediately unregister the service"; application identified by object path + D-Bus connection; errors `InvalidArguments`, `AlreadyExists` — [BlueZ org.bluez.GattManager.rst](https://raw.githubusercontent.com/bluez/bluez/master/doc/org.bluez.GattManager.rst)
- `WriteValue` options passed to the server: `offset`, `type` = `"command"` (write without response) / `"request"` (write with response) / `"reliable"`, plus server-only `mtu`, `device`, `link` ("BR/EDR"/"LE") and `prepare-authorize` — [BlueZ org.bluez.GattCharacteristic.rst](https://raw.githubusercontent.com/bluez/bluez/master/doc/org.bluez.GattCharacteristic.rst)
- MTU: "the MTU can only be negotiated once and is symmetric"; read-only `MTU` property; "For server the MTU returned shall be equal or smaller than the negotiated MTU" — [same doc](https://raw.githubusercontent.com/bluez/bluez/master/doc/org.bluez.GattCharacteristic.rst)
- Indications: server-side optional method `Confirm()` (noreply) "Confirms value was received" — this is how a BlueZ GATT server application learns that the client confirmed an indication — [same doc](https://raw.githubusercontent.com/bluez/bluez/master/doc/org.bluez.GattCharacteristic.rst)
- `AcquireNotify` (fd-based): for servers, once a confirmation arrives one byte 0x01 is written to the fd; `AcquireWrite` requires the `write-without-response` flag (so not usable for the contract's write-with-response RX) — [same doc](https://raw.githubusercontent.com/bluez/bluez/master/doc/org.bluez.GattCharacteristic.rst)
- Flags available include `write`, `indicate`, `encrypt-write`, `encrypt-authenticated-*`, `secure-*`, `authorize`; the doc itself does not state a 512-byte max — [same doc](https://raw.githubusercontent.com/bluez/bluez/master/doc/org.bluez.GattCharacteristic.rst)
- BlueZ's reference server emits notifications by `PropertiesChanged(GATT_CHRC_IFACE, {'Value': value}, [])`, uses `dbus.mainloop.glib.DBusGMainLoop(set_as_default=True)` + `GLib.MainLoop()`, and registers via `GattManager1.RegisterApplication(app.get_path(), {}, ...)` — [BlueZ test/example-gatt-server](https://raw.githubusercontent.com/bluez/bluez/master/test/example-gatt-server)
- Library landscape: **bless** (kevincar/bless, MIT, cross-platform GATT server in Bleak style, ~162 stars, last push > 1 year before index snapshot) — [ecosyste.ms](https://science.ecosyste.ms/projects/63887); **bluez-peripheral** (BlueZ GATT API wrapper) — [PyPI](https://pypi.org/project/bluez-peripheral/0.1.5/); **PyBLEz** — [PyPI](https://pypi.org/project/PyBLEz); **bluezero** has a peripheral example but requires D-Bus permission config — [PyPI](https://pypi.python.org/pypi/bluezero); raw-D-Bus tutorial reusing BlueZ example code on Pi — [scribles.net](https://scribles.net/creating-ble-gatt-server-uart-service-on-raspberry-pi/). Whether bless's Linux backend uses dbus-next or dbus-fast was **not confirmed**.

### Inferences
- **Recommendation: raw BlueZ D-Bus with dbus-python + GLib**, matching the contract text ("máy BlueZ D-Bus GATT Application, giữ GLib hiện có"). Reasons: (1) zero new dependency; Debian packages `python3-dbus`, `python3-gi` are system packages; (2) direct access to `options['mtu']` and `options['device']` per WriteValue, which is needed to compute fragment size (MTU-3) for TX and to enforce "one connection, second rejected"; (3) direct `Confirm()` hook to gate the next TX fragment ("TX đợi indication confirmation"). An asyncio alternative (dbus-fast, used by Home Assistant/Bleak) is reasonable only if the rest of the machine code moves to asyncio; mixing it with the existing GLib loop is not worth it.
- Skeleton (unverified details from BlueZ docs/experience): objects `/flexmix/app` (ObjectManager) → `/flexmix/app/service0` (UUID `8b9bf000-…`, Primary=True) → `char0` RX (Flags `["write"]`, optionally `["encrypt-write"]` is NOT wanted because contract forbids bonding) and `char1` TX (Flags `["indicate"]`; BlueZ creates CCCD automatically). Advertisement object implementing `org.bluez.LEAdvertisement1` with `Type="peripheral"`, `ServiceUUIDs=[service UUID]`, short `LocalName`; register on `LEAdvertisingManager1` of `/org/bluez/hci0`. Legacy advertising payload is 31 bytes; a 128-bit UUID (18 bytes incl. header) + flags (3) leaves ~10 bytes for name, so put the name/serial-derived name in scan response or keep it short (unverified sizing; verify with `btmon`).
- Indication flow with BlueZ (unverified, validate with btmon): set `Value` and emit `PropertiesChanged`; bluetoothd sends ATT Handle Value Indication; when the client's confirmation arrives, bluetoothd calls the app's `Confirm()`. Implement TX as a queue that sends fragment n+1 only after `Confirm()` for fragment n; add a per-fragment timeout (ATT transaction timeout is 30 s by spec; the contract's 10 s packet timeout is stricter and will dominate).
- Fragment size: take `mtu` from the latest `WriteValue`/`StartNotify` context (or read `Device1`/characteristic `MTU` property), fragment TX at `mtu-3`; never assume 517. BlueZ's default LE MTU on its server side is 517 in recent versions, but Android may end up with 247/512 etc. (unverified).
- 512-byte attribute max: ATT spec caps attribute value at 512 bytes (Bluetooth Core spec, not fetched). With MTU-3 fragments (≤514) it is fine for RX if Android requests MTU ≤ 515; with MTU 517 a single write payload can be 514 bytes > 512 — **cap RX fragment size at min(MTU-3, 512)**. Android itself rejects writes > 512 on recent versions (unverified).
- Single-connection enforcement: BlueZ has no per-service "max 1 connection" switch; implement in app: remember first `device` path, reject writes from others with `org.bluez.Error.NotPermitted`, and call `Device1.Disconnect()` on intruders; stop advertising while a session is active (`UnregisterAdvertisement`), re-register on disconnect (listen for `Device1.Connected=False` PropertiesChanged).
- Do not let `RequireAuthentication`/agent logic from the SPP code leak in: no agent is needed for unbonded GATT; if a previous agent sets `Pairable=True`, Android might trigger bonding prompts on encrypted characteristics — keep flags unencrypted since security is HPKE at app layer.
- systemd: run as dedicated user (e.g., `flexmix`) only if D-Bus policy allows registering GATT apps; by default `/usr/share/dbus-1/system.d/bluetooth.conf` allows root and (on Debian) group `bluetooth` to talk to `org.bluez` (unverified; check the file on the Pi). Unit: `After=bluetooth.service`, `Requires=bluetooth.service`, `Restart=on-failure`, `RestartSec=2`; on start, re-register app/advert (bluetoothd restart drops registrations — subscribe to `NameOwnerChanged` for `org.bluez`). Ensure `/etc/bluetooth/main.conf` is not forcing `ControllerMode=bredr`; leave `dual` or set `le`. Unblock rfkill (`rfkill unblock bluetooth`) — Pi OS images may soft-block radios until Wi-Fi country is set (unverified).

## Q2. Android side: permissions, MTU, op queue, API 33 changes, status 133, plugin vs native

### Takeaway
Use **native Kotlin `BluetoothGatt` behind MethodChannel `flexmix/pairing`** as the contract already states; a strictly serialized GATT operation queue, `requestMtu(517)` completed before any data is exchanged, `CONNECTION_PRIORITY_HIGH` during provisioning, API-33 `writeCharacteristic(c, value, type)` with int status, and "close + reconnect" as the 133 strategy. flutter_blue_plus now requires a **paid commercial licence for for-profit use**, which is a concrete reason not to adopt it.

### Cited Findings
- Android 12+: `BLUETOOTH_SCAN` for discovery, `BLUETOOTH_CONNECT` to communicate; both runtime ("Nearby devices" prompt); legacy `BLUETOOTH`/`BLUETOOTH_ADMIN` with `maxSdkVersion="30"`; `usesPermissionFlags="neverForLocation"` on BLUETOOTH_SCAN allows dropping ACCESS_FINE_LOCATION (set its `maxSdkVersion="30"`), but "some BLE beacons are filtered from the scan results" — [Android Developers: Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)
- Status 133 = GATT_ERROR (0x85), undocumented and generic; recommended recovery is to close `BluetoothGatt` and call `connectGatt` again; serialize GATT ops in a FIFO queue — [Punch Through: 4 Tips to Make Android BLE Actually Work](https://punchthrough.com/android-ble-development-tips/) (via search snippet; page fetch failed). Older guidance: call only `close()` (not `disconnect()` immediately before), run GATT ops on one thread, small delay after 133/128 is anecdotal — [jlelse lessons](https://android.jlelse.eu/lessons-for-first-time-android-bluetooth-le-developers-i-learned-the-hard-way-fee07646624). Nordic DevZone: 133 can come from collisions, timeouts, after airplane mode — [Nordic DevZone](https://devzone.nordicsemi.com/f/nordic-q-a/60017/android---error-133-0x85-gatt-error---only-after-returning-from-flight-mode/245346)
- flutter_blue_plus: on Android requests MTU 512 by default during connect; `allowLongWrite` (≤512 bytes, with response, may leave characteristic partially written, slow at small MTU); suggested `splitWrite` chunks at `mtuNow-3`; `ANDROID_SPECIFIC_ERROR` has "no 100% solution", catch and retry; operations queued globally by default (`OperationQueueMode.perDevice` optional); **licence: free for personal/nonprofit/educational, for-profit use requires a Commercial License** — [flutter_blue_plus README](https://raw.githubusercontent.com/chipweinberger/flutter_blue_plus/master/packages/flutter_blue_plus/README.md)
- flutter_reactive_ble (PhilipsHue, verified publisher meethue.com): not archived; last push 2026-04-01, v5.4.x, ~135 open issues — [depscope](https://mcp.depscope.dev/pkg/pub/flutter_reactive_ble); [gittrend](https://gittrend.io/repo/PhilipsHue/flutter_reactive_ble)
- `BluetoothGatt` API 33 changes (from model summary of developer.android.com reference; page truncated, **treat as needs re-check**): `writeCharacteristic(characteristic, value, writeType)` returns `int` (`BluetoothStatusCodes.SUCCESS`, `ERROR_GATT_WRITE_REQUEST_BUSY`…), old boolean variant deprecated; `writeDescriptor(descriptor, value)` likewise; `onCharacteristicChanged(gatt, characteristic, value: ByteArray)` new signature; `requestMtu` range 23–517 with result in `onMtuChanged`; `requestConnectionPriority(HIGH|BALANCED|LOW_POWER)` — [Android BluetoothGatt reference](https://developer.android.com/reference/android/bluetooth/BluetoothGatt)

### Inferences
- **Recommendation: native Kotlin.** The contract already fixes MethodChannel `flexmix/pairing` and keeps S, HPKE contexts and Wi-Fi password in native RAM (Bouncy Castle 1.86 in Kotlin). Routing GATT through a Dart plugin would force secret-bearing ciphertext/plain frames across the Dart boundary anyway, and require fine control (write callback before next fragment, indication ordering, generation handle) that plugins abstract away. flutter_blue_plus's commercial licence is an additional blocker for a product; flutter_reactive_ble is viable but redundant.
- Kotlin design (unverified best-practice, consistent with Punch Through): one `HandlerThread`/coroutine single-thread dispatcher owning `BluetoothGatt`; a `GattOp` queue (connect → discoverServices → requestMtu(517) → requestConnectionPriority(HIGH) → writeDescriptor(CCCD 0x0002 on TX) → app "hello" wait). Each op completes only on its callback, with a per-op timeout (e.g., 5–10 s) that triggers `close()` and session failure (`PAIRING_TRANSPORT_ERROR`). Every callback carries/compares the connection generation (contract §generation handle).
- Order: many stacks accept MTU request before or after discovery; commonly recommended is `requestMtu` right after `onConnectionStateChange(CONNECTED)` and before `discoverServices`, or after discovery — both work; pick one and wait for `onMtuChanged`. Use the returned `mtu` (could be 247, 512, 517…), not the requested value. Fragment RX = `min(mtu-3, 512)`.
- `connectGatt(context, device, autoConnect=false, callback, TRANSPORT_LE)` — always pass `TRANSPORT_LE` (otherwise dual-mode Pi may be connected over BR/EDR and GATT over classic, a known 133 trigger; unverified). On 133 during connect: `close()`, wait ~500 ms–1 s, retry up to 2–3 times, then surface `PAIRING_TRANSPORT_ERROR`.
- Service cache: if the Pi's GATT database changes between dev builds, Android may cache old handles; either add the Service Changed characteristic (BlueZ provides GATT service with Service Changed) or use hidden `refresh()` reflectively only in debug builds (unverified).
- Scanning: filter by service UUID (`ScanFilter.setServiceUuid`) so `neverForLocation` is safe (no location derivation); stop scan before connecting (scanning during connect hurts reliability, unverified).
- Disconnect cleanup: on `onConnectionStateChange(DISCONNECTED)` or any error, invalidate generation, `gatt.close()`, zero buffers per contract.

### Gaps
- Could not fetch the full Android `BluetoothGatt` reference and Punch Through guide text; API 33 details above should be double-checked against the live reference before coding.
- No reliable source for which Android versions reject >512-byte writes, or for `WRITE_TYPE_DEFAULT` behaviour when value > MTU-3 (Android performs a long write/prepare-write automatically in some versions — unverified).

## Q3. Framing: is u32be length + JSON right? Long write vs chunking; throughput

### Takeaway
The contract's design (application-level u32be length prefix, MTU-3 fragments, write-with-response per fragment, indications with confirmation, strict FIFO) is the right choice: GATT long/reliable writes are capped at 512 bytes per attribute and leave partial state on interruption, so they cannot carry an 8192-byte packet anyway. Sequence numbers are unnecessary because both directions are acknowledged at ATT level and in-order on a single link.

### Cited Findings
- Long write (`allowLongWrite`) is limited to 512 bytes, requires with-response, peripheral must support it, interrupted transfer may leave characteristic partially written, slow at small MTU; chunking at `mtu-3` with response is the alternative — [flutter_blue_plus README](https://raw.githubusercontent.com/chipweinberger/flutter_blue_plus/master/packages/flutter_blue_plus/README.md)
- BlueZ passes `offset` and `type: "reliable"` / `prepare-authorize` to servers for prepare/execute writes — the server app must handle offsets itself — [BlueZ GattCharacteristic](https://raw.githubusercontent.com/bluez/bluez/master/doc/org.bluez.GattCharacteristic.rst)

### Inferences
- Keep the length-prefix; reject `offset != 0` on RX (`org.bluez.Error.InvalidOffset`) so accidental Android long-writes fail loudly instead of corrupting the reassembly buffer. Reject writes whose `type != "request"`.
- Sequence numbers would only help with write-without-response or multiple outstanding indications; the contract forbids both. ATT write-with-response + indication-confirm already gives one-in-flight, ordered delivery. Integrity/replay is covered by HPKE AEAD + transcript hashes.
- Throughput estimate (unverified, back-of-envelope): one write-with-response round-trip costs ~2 connection events. At connection interval 7.5–15 ms (HIGH priority) and 244–509-byte fragments, expect roughly 10–40 KB/s; at MTU 23 (20-byte fragments) and 30–50 ms interval, ~0.5–1 KB/s, i.e., an 8 KB packet could take ~10–16 s — **exceeding the 10 s packet timeout**. Real packets here are small (hello ~300 B, requests with enc+ct perhaps 300–600 B b64), so MTU23 worst case is still a few seconds, but test the max-size packet at MTU 23 against the 10 s timeout (contract gate 4 tests MTU23 fragments).
- Optionally the Pi can request a short connection interval itself; Android `CONNECTION_PRIORITY_HIGH` is the practical lever.

## Q4. Wi-Fi configuration on Raspberry Pi OS: NetworkManager API, success detection, rollback, permissions, coexistence

### Takeaway
Raspberry Pi OS Bookworm (and Trixie) use **NetworkManager** by default, so use the **NetworkManager D-Bus API** (from the same dbus-python/GLib process or a small helper) rather than wpa_supplicant/wpa_cli or parsing `nmcli`. Add the new profile with `AddAndActivateConnection2`, watch `Connection.Active` `StateChanged` to `ACTIVATED (2)` = association + IP config done, treat `DEACTIVATED(4)`/device `FAILED(120)` or a timeout as failure, and roll back by re-activating the saved previous connection and deleting the new one. NM **checkpoints** (`CheckpointCreate` with `rollback_timeout`) provide an atomic, crash-safe rollback primitive.

### Cited Findings
- Bookworm switched default networking from dhcpcd to NetworkManager; `/etc/dhcpcd.conf` absent on fresh installs, `nmcli` is the replacement; upgraded-in-place systems may still use dhcpcd (anecdotal) — [OMG! Linux](https://www.omglinux.com/raspberry-pi-os-bookworm/); [DEV Community/Blues](https://dev.to/blues/the-easiest-way-to-upgrade-raspberry-pi-os-from-bullseye-to-bookworm-c3m); [Pi-hole discourse](https://discourse.pi-hole.net/t/raspberry-pi-os-bookworm-is-out-now-pihole-error-unsupported-os-detected-debian-12/65480). Official RPi announcement not fetchable (DNS) — secondary sources only.
- `AddAndActivateConnection2` option `persist`: `"disk"` (default), `"memory"` (not saved to disk), `"volatile"` (not saved, destroyed when disconnected); `bind-activation: "dbus-client"` auto-disconnects when the requesting process leaves the bus (default `"none"`) — [NM introspection XML](https://raw.githubusercontent.com/NetworkManager/NetworkManager/main/introspection/org.freedesktop.NetworkManager.xml)
- Checkpoints: `CheckpointCreate(devices, rollback_timeout, flags)` — empty device list = all devices; non-zero `rollback_timeout` auto-rolls back after that time; `CheckpointRollback` rolls back early; `CheckpointDestroy` commits/discards; `CheckpointAdjustRollbackTimeout` extends from "now" — [NM introspection XML](https://raw.githubusercontent.com/NetworkManager/NetworkManager/main/introspection/org.freedesktop.NetworkManager.xml)
- Enum values — `NMActiveConnectionState`: UNKNOWN 0, ACTIVATING 1, ACTIVATED 2, DEACTIVATING 3, DEACTIVATED 4. `NMActiveConnectionStateReason`: … IP_CONFIG_INVALID 5, CONNECT_TIMEOUT 6, NO_SECRETS 9, LOGIN_FAILED 10, CONNECTION_REMOVED 11 … `NMDeviceState`: DISCONNECTED 30, PREPARE 40, CONFIG 50, NEED_AUTH 60, IP_CONFIG 70, IP_CHECK 80, SECONDARIES 90, ACTIVATED 100, DEACTIVATING 110, FAILED 120. `NMDeviceStateReason`: IP_CONFIG_UNAVAILABLE 5, IP_CONFIG_EXPIRED 6, NO_SECRETS 7, SUPPLICANT_DISCONNECT 8, SUPPLICANT_CONFIG_FAILED 9, SUPPLICANT_FAILED 10, SUPPLICANT_TIMEOUT 11, DHCP_START_FAILED 15, DHCP_ERROR 16, DHCP_FAILED 17, SSID_NOT_FOUND 53. `NMCheckpointCreateFlags`: DESTROY_ALL 0x01, DELETE_NEW_CONNECTIONS 0x02, DISCONNECT_NEW_DEVICES 0x04, ALLOW_OVERLAPPING 0x08 … `NMConnectivityState`: NONE 1, PORTAL 2, LIMITED 3, FULL 4 — [nm-dbus-interface.h](https://raw.githubusercontent.com/NetworkManager/NetworkManager/main/src/libnm-core-public/nm-dbus-interface.h)
- `Connection.Active` emits `StateChanged(u state, u reason)` — [NM API docs (search result)](https://networkmanager.dev/docs/api/latest/gdbus-org.freedesktop.NetworkManager.Connection.Active.html)
- Polkit: changing system connections is governed by `org.freedesktop.NetworkManager.settings.modify.system`; Wi-Fi scan is separate `org.freedesktop.NetworkManager.wifi.scan`; custom rules go in `/etc/polkit-1/rules.d/`; editing `/usr/share` policy is lost on upgrade — [slatecave](https://slatecave.net/blog/networkmanager-group-using-polkit/); [Launchpad](https://bugs.edge.launchpad.net/ubuntu/+source/network-manager/+bug/964705/comments/19); [Fedora wiki](https://fedoraproject.org/wiki/Features/NetworkManagerSystemConnections) (forum-quality sources, no verified example rule found)
- balena **wifi-connect** "interacts with NetworkManager" (NM must be the active manager); on failure re-enables its AP for retry; on success NM saves the configuration — [wifi-connect README](https://raw.githubusercontent.com/balena-os/wifi-connect/master/README.md)
- BT/Wi-Fi coexistence: a CYW43455 Bluetooth firmware update (BCM4345C0 .hcd) fixed failure to accept BLE connections — [raspberrypi/linux#3689](https://github.com/raspberrypi/linux/issues/3689); similar random BLE drops (reason timeout) under simultaneous Wi-Fi on BCM43430, more frequent when the AP goes down — [Infineon community](https://community.infineon.com/t5/Other-Technologies-General/Bluetooth-disconnection-when-using-Wi-Fi-on-bcm43430/m-p/404020)

### Inferences
- **Recommendation: NM D-Bus via dbus-python in the pairing daemon (or a tiny root helper), not nmcli parsing, not wpa_cli.** wpa_supplicant is driven by NM on Bookworm+; touching it directly fights NM. nmcli is acceptable as a fallback/diagnostic (`nmcli -w 30 dev wifi connect SSID password … ifname wlan0` blocks with timeout) but output parsing and passing the password on argv (visible in `/proc/*/cmdline`) conflict with "không log/echo password". Libraries: `python-sdbus-networkmanager` (sd-bus based) or `dbus-next`/`dbus-fast` are fine but add a second D-Bus stack; plain dbus-python suffices (unverified preference).
- **Algorithm for `configure_wifi(ssid, password, timeout)`** (unverified, assemble from API above):
  1. Record previous state: `Device(wlan0).ActiveConnection` → its `Connection` settings path/UUID (may be none, e.g. first-time setup with no Wi-Fi or Ethernet-only).
  2. Optional safety net: `CheckpointCreate([wlan0_path], rollback_timeout=T+15, flags=DELETE_NEW_CONNECTIONS|DESTROY_ALL)` so a daemon crash mid-switch still auto-restores the old network and deletes the half-created profile. On success call `CheckpointDestroy` (commit); on failure call `CheckpointRollback`. Checkpoint semantics on Wi-Fi with secrets should be verified on the Pi (gate 5).
  3. Build settings: `connection{id:"flexmix-<ssid>", type:"802-11-wireless", uuid:new, autoconnect:true, autoconnect-priority:10}`, `802-11-wireless{ssid:bytes, mode:"infrastructure"}`, `802-11-wireless-security{key-mgmt:"wpa-psk", psk:password}` (open networks: omit security; WPA3-SAE: `key-mgmt:"sae"` — decide whether contract supports it), `ipv4{method:"auto"}`, `ipv6{method:"auto"}`. Call `AddAndActivateConnection2(settings, wlan0, "/", {persist:"memory"})` first; only after success `Update2`/`Save()` to disk ("keep credentials" requirement), so a failed attempt never persists. Alternative: `persist:"disk"` + delete on failure (simpler, but leaves secret on disk briefly).
  4. Wait on `Connection.Active.StateChanged`: `ACTIVATED(2)` ⇒ success (NM reaches ACTIVATED only after association/auth and IP config; with default `ipv4.may-fail=yes` and `ipv6` auto, NM may declare ACTIVATED when *either* family succeeds — for strict "DHCP success" set `ipv4.may-fail=false` and then also check `Ip4Config.AddressData` non-empty, unverified). `DEACTIVATED(4)` with reason (NO_SECRETS 9 → wrong password; CONNECT_TIMEOUT 6; IP_CONFIG_INVALID 5 → DHCP) or device `StateChanged` to FAILED(120) with SSID_NOT_FOUND 53 / SUPPLICANT_* / DHCP_* ⇒ failure. Also enforce overall timeout (e.g., 30–45 s; NM's own wifi auth timeout ~25 s and DHCP timeout 45 s by default — unverified, set `ipv4.dhcp-timeout` explicitly e.g. 30).
  5. Do **not** use `NMConnectivityState`/server reachability as Wi-Fi success (matches user decision: keep new Wi-Fi even if server unreachable).
  6. Rollback on failure: `DeleteConnection` the new profile, `ActivateConnection(prev_conn, wlan0, "/")` (or `CheckpointRollback`), and wait for prev ACTIVATED (best-effort; report WIFI_FAILED regardless).
  7. Map to contract errors: wrong password/SSID not found/DHCP fail → `WIFI_FAILED`; generation invalid → cancel: call `DeactivateConnection` + rollback before reporting.
- Autoconnect: give the new profile higher `autoconnect-priority` than the old one, keep the old profile (do not delete) so NM can fall back if the new AP disappears later; optionally set `connection.autoconnect-retries`. Avoid `bind-activation:"dbus-client"` (would drop Wi-Fi when the daemon restarts).
- Privileges: simplest is running the network helper as root under systemd with hardening (`ProtectSystem=strict`, `ReadWritePaths=` for config, `NoNewPrivileges`, `CapabilityBoundingSet=`). Non-root alternative: dedicated user + polkit JS rule in `/etc/polkit-1/rules.d/50-flexmix.rules` returning `polkit.Result.YES` for `subject.user=="flexmix"` on `org.freedesktop.NetworkManager.network-control`, `.settings.modify.system`, `.enable-disable-wifi`, `.wifi.scan`, and `.checkpoint-rollback` (action names unverified — list with `pkaction | grep NetworkManager` on the Pi). ## Q5. Activation retry job: backoff schedule and persistence across restart

### Takeaway
Use capped exponential backoff with **full jitter** (sleep = random(0, min(cap, base·2^n))), e.g. base 5 s, cap 15–30 min, no total give-up while unactivated but with a small attempt counter for diagnostics; persist only non-secret job state (challenge_id / attempt / next_at) atomically, and let a systemd service (`Restart=on-failure`) or timer resume it after reboot.

### Cited Findings
- AWS: capped exponential backoff alone still clusters retries; adding jitter (full jitter) reduces client work and contention; most AWS SDKs now implement backoff + jitter — [AWS Architecture Blog: Exponential Backoff and Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/); Well-Architected REL05-BP03 recommends capping backoff and limiting retries — [AWS Well-Architected](https://docs.aws.amazon.com/en_us/wellarchitected/2022-03-31/framework/rel_mitigate_interaction_failure_limit_retries.html)
- Full-jitter pseudocode `sleep = random_between(0, min(cap, base * 2**attempt))` — [blackglory notes (secondary)](https://blackglory.me/notes/algorithms-and-data-structures/Algorithms/Exponential_Backoff/Exponential_Backoff_with_Jitter_(Recommended)?variant=en)

### Inferences
- Suggested schedule (unverified recommendation for Planner to lock): attempt n sleep = uniform(0, min(1800 s, 5 s·2^n)) with a floor of ~2 s; reset backoff on NM connectivity change to FULL (subscribe to NM `StateChanged`/`Connectivity` signals — used only as a trigger, not as Wi-Fi success); "decorrelated jitter" is an acceptable alternative.
- Persistence: one JSON file `/var/lib/flexmix/activation_job.json` (0600, written via temp file + `fsync` + `rename`), containing only `{job_state, challenge_id?, attempt, next_attempt_at_wallclock, last_error_code}` — never S, seal_code, password, HPKE context (contract forbids). On restart: if `challenge_id` pending and possibly committed, first query result/bind status on server before creating a new challenge (contract "unknown commit" gate). Use `systemd` `StateDirectory=flexmix` for the directory, `Restart=on-failure` + `RestartSec=5`, `StartLimitIntervalSec=0` to avoid systemd giving up; the job loop itself handles backoff (don't use systemd restart as the backoff mechanism). A `systemd.timer` with `RandomizedDelaySec` is an alternative but adds a second scheduler; a single long-running daemon with GLib `timeout_add_seconds` fits the existing GLib loop.
- Use monotonic clock for in-process waits and wall-clock only for the persisted `next_attempt_at` (Pi has no RTC — Pi 5 has an RTC only with a battery; after boot without NTP the wall clock may be wrong — so on restart treat a "next_at" in the future by more than cap as "now").
- Ensure single job per machine: file lock (`fcntl.flock`) on the state file or single systemd unit instance.
