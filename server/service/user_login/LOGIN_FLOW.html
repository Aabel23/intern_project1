Luồng đăng nhập

Đăng nhập đi qua hai request. Lần đầu app gửi username và mật khẩu, server kiểm tra ngay và giữ kết quả trong bộ nhớ. Lần hai app hỏi lấy kết quả đó, và nếu đúng mật khẩu thì nhận luôn token.

API và gói tin

Mọi gói là JSON gửi bằng POST. Đăng nhập chưa cần token; token trả về ở bước xác minh được app gửi kèm mọi request sau đó. Hai route đăng nhập bị giới hạn 30 request/phút/IP.

Phương thứcRouteAi gọiGửi lênNhận về

Gửi tài khoản

{"request_id": "<32 ký tự hex>", "username": "vana", "password": "..."}
→ {"valid": true, "login_id": "...", "verify_route": "/app/xac-minh-dang-nhap", "message": "Đã nhận yêu cầu đăng nhập"}

Hỏi kết quả

{"request_id": "...", "login_id": "..."}
→ {"valid": true, "verified": true, "token": "<43 ký tự>", "message": "Đăng nhập thành công"}

Đăng xuất

{"token": "..."}
→ {"valid": true, "message": "Đã đăng xuất"}

Giai đoạn A: App gửi yêu cầu đăng nhập

1auth_page.dart, hàm _AuthPageState._submit() (dòng 58)

Chạy khi người dùng bấm nút đăng nhập (dòng 394) hoặc nhấn Enter ở ô mật khẩu (dòng 372).

  1. Đang xử lý (_busy) thì bỏ qua, để bấm nhiều lần không gửi nhiều request.
  2. Gọi _formKey.currentState!.validate() để kiểm tra các ô đã nhập hợp lệ chưa.
  3. Đặt _busy = true để khóa nút.
  4. Đang ở chế độ đăng nhập (!_register) thì gọi requestLogin(...).

2login_request.dart, hàm requestLogin()

  1. Tạo requestId: 16 byte ngẫu nhiên, viết thành 32 ký tự hex. Đây là mã của lần đăng nhập này, dùng để ghép hai request với nhau.
  2. Request 1: gọi postRegistrationJson(serverUrl, '/app/dang-nhap', {request_id, username, password}).
  3. Server báo lỗi (valid == false) thì trả lỗi đó luôn.
  4. Request 2: gọi postRegistrationJson(serverUrl, '/app/xac-minh-dang-nhap', {request_id, login_id}), trong đó login_id là mã server vừa trả ở request 1.

3registration_request.dart, hàm postRegistrationJson()

Hàm gửi HTTP dùng chung cho cả đăng ký và đăng nhập:

  1. Tạo HttpClient, chờ kết nối tối đa 5 giây.
  2. Chuyển dữ liệu thành JSON, gửi POST tới serverUrl + path.
  3. Đọc phản hồi, giải mã JSON thành Map rồi trả về. Cả quá trình tối đa 25 giây.
  4. Hàm không xem mã HTTP (200 hay 400) mà chỉ đọc JSON, nên kết quả được hay không nằm ở trường valid.

Giai đoạn B: Server nhận request 1 (/app/dang-nhap)

4server/main.py

  • Hàm main() (dòng 101): gọi init_db() để tạo bảng nếu chưa có, rồi serve_forever() lắng nghe cổng 8000.
  • Hàm Handler.do_POST() (dòng 31) nhận mọi request POST:
    1. Đường dẫn thuộc nhóm relay (gửi lệnh, heartbeat) thì chuyển sang code relay.
    2. Tra bảng ROUTES và thấy /app/dang-nhap ứng với hàm receive_login.
    3. Gọi too_many_requests() (dòng 66): một địa chỉ IP quá 30 request trong một phút thì trả mã 429.
    4. Đọc body, chỉ nhận từ 1 đến 4096 byte, giải mã JSON rồi gọi receive_login(data).
    5. Có lỗi JSON thì trả 400, lỗi database thì trả 503.
    6. Gọi send_json() (dòng 80) trả kết quả: 200 nếu valid là true, 400 nếu false, 429 nếu kết quả có retry_after.

5login_flow.py, hàm receive_login(data)

Hàm này quản lý các lần đăng nhập đang diễn ra, lưu trong biến LOGIN_STATES trên bộ nhớ:

  1. Kiểm tra request_id đúng dạng 32 ký tự hex.
  2. Tạo fingerprint: mã HMAC của toàn bộ gói dữ liệu, để nhận ra khi cùng request_id nhưng nội dung đã bị đổi.
  3. Giữ khóa FLOW_LOCK rồi:
    • Gọi cleanup_locked() để xóa các lần đăng nhập quá 60 giây.
    • Gọi find_login(request_id). Nếu request_id này đã gửi rồi (app gửi lại vì mạng chập chờn):
      • cùng fingerprint thì trả lại login_id cũ, không kiểm tra lại mật khẩu;
      • khác fingerprint thì báo lỗi dữ liệu đã thay đổi.
    • Đang có quá 1000 lần đăng nhập dở thì báo server bận.
    • Tạo login_id ngẫu nhiên và lưu {request_id, fingerprint, status: "received", hết hạn sau 60 giây}. Mật khẩu không được lưu.
  4. Gọi verify_login(data) để kiểm tra mật khẩu, lúc này không giữ khóa.
  5. Giữ khóa lại, đổi status thành "verified" và lưu kết quả vào result.
  6. Trả cho app {valid: true, login_id, verify_route}. Dù mật khẩu sai, bước này vẫn trả valid: true, vì nó chỉ xác nhận "đã nhận yêu cầu".

6login_verify.py, hàm verify_login(data)

  1. Kiểm tra username và mật khẩu có giá trị, username tối đa 150 ký tự, mật khẩu tối đa 1024.
  2. Gọi get_credentials(username) để lấy mật khẩu đã băm trong database.
  3. Nếu không có user này thì dùng DUMMY_PASSWORD: vẫn băm và so sánh như bình thường, để thời gian trả lời giống hệt trường hợp sai mật khẩu. Kẻ xấu không đo thời gian để đoán username nào tồn tại được.
  4. Gọi _matches_password() để so mật khẩu.
  5. Sai thì trả thông báo chung "Tên đăng nhập hoặc mật khẩu không đúng", không nói sai phần nào.
  6. Đúng thì gọi create_session(credentials["id"]) và trả {valid: true, verified: true, token, message}.

7user_read.py, hàm get_credentials(username)

Chạy SELECT id, username, password FROM users WHERE username = ?. Chỉ hàm này đọc cột mật khẩu, và kết quả không bao giờ được gửi về app.

8login_verify.py, hàm _matches_password(password, stored)

  1. Tách chuỗi đã lưu theo dạng pbkdf2_sha256$số_vòng$salt$mã_băm.
  2. Băm lại mật khẩu vừa nhập bằng hashlib.pbkdf2_hmac với cùng salt và số vòng.
  3. So sánh bằng hmac.compare_digest. Hàm này luôn so hết chuỗi nên thời gian như nhau dù sai ở ký tự nào.

9session.py, hàm create_session(user_id)

  1. Xóa các phiên đã hết hạn trong app_sessions.
  2. Tạo token = secrets.token_urlsafe(32).
  3. Lưu SHA-256(token), user_id và hạn 30 ngày vào app_sessions.
  4. Trả token gốc về cho verify_login.

10connection.py, hàm get_connection()

Mọi thao tác database ở trên đều đi qua hàm này. Nó mở SQLite, bật khóa ngoại (foreign_keys), tự lưu thay đổi khi mọi thứ ổn và tự hủy thay đổi khi có lỗi.

Giai đoạn C: App hỏi kết quả (/app/xac-minh-dang-nhap)

11main.py, hàm Handler.do_POST()

Đi đúng các bước như ở mục 4, lần này ROUTES trỏ tới send_verification.

12login_flow.py, hàm send_verification(data)

  1. Kiểm tra request_id và login_id có đúng dạng.
  2. Xóa các lần đăng nhập quá hạn, rồi tìm theo login_id:
    • không thấy thì báo "đã hết hạn";
    • request_id không khớp thì báo lỗi. So sánh bằng compare_digest nên người khác cầm login_id cũng không lấy được kết quả;
    • chưa kiểm tra xong thì trả retry_after: 1, và server gửi mã 429.
  3. Kiểm tra xong thì trả result, tức kết quả của verify_login: {valid, verified, token, message} khi đúng mật khẩu, hoặc {valid: false, message} khi sai.

Giai đoạn D: App xử lý kết quả

13auth_page.dart, tiếp tục trong _submit()

  1. Màn hình đã đóng (!mounted) thì dừng.
  2. valid != true thì gọi _showMessage() (dòng 144) hiện thông báo lỗi dưới dạng SnackBar.
  3. Đúng mật khẩu thì dùng Navigator.pushReplacement chuyển sang MainDashboard(serverUrl, token: result['token']). Màn đăng nhập bị thay hẳn nên bấm Back không quay lại được.
  4. Cuối cùng mở khóa nút: _busy = false.

14main_dashboard.dart

Tạo MachineApi(serverUrl, token: token) để giữ token, rồi gọi loadMyMachines() lấy danh sách máy.

Vài điểm cần biết

  • Tách hai request để app gửi lại an toàn. Nếu mạng rớt giữa chừng, app gửi lại đúng request_id cũ thì nhận lại login_id cũ. Server không tạo phiên mới, cũng không kiểm tra lại mật khẩu.
  • Kết quả nằm trong RAM 60 giây. Server khởi động lại trong khoảng đó thì app phải đăng nhập lại.
  • Token chỉ trả ở bước 2, không trả ở bước 1. Muốn lấy token phải có đủ cả login_id lẫn request_id.
  • Hiện tại app chưa xử lý retry_after. Nếu request 2 đến lúc server chưa kiểm tra mật khẩu xong, app sẽ hiện luôn thông báo "Đang xác minh đăng nhập" thay vì chờ và hỏi lại. Chuyện này khó xảy ra, vì ở request 1 server kiểm tra mật khẩu xong rồi mới trả lời.
